# BauAI Data Migration Plan — Supabase (Postgres) → MongoDB

| | |
|---|---|
| **Companion to** | `bauai-nextjs-migration-proposal.md` (Section 5.2 / Phase 2) |
| **Status** | Proposed — based on **live inspection of both databases on 2026-08-11** |
| **Source** | Supabase Postgres `wbzknpogcrjmomazpjoj` (production; service-role read) — 132 tables, 99 RPCs, 19 storage buckets |
| **Target** | MongoDB `mongodb://localhost:27018/bauai` (`atlas-local` 8.2; today a dev/staging instance) — 45 collections |
| **Method** | Read-only. Row counts via PostgREST `Content-Range` (exact); schemas via one-row samples; Mongo via `mongosh` + the `models/` definitions. No data was written or deleted. |

> **The one-sentence version:** the hard part of a data migration — the 8-million-row tender corpus — **does not need migrating at all** (the new pipeline re-ingests it, and already has: 44,865 tenders are live in Mongo). What must move is a **small, high-value tenant dataset** (268 companies, ~450 users, their saved tenders, documents, chat, and billing). Most of that is mechanical; **three things are genuinely hard: auth password hashes, Stripe billing, and anything whose target schema doesn't exist yet.**

## 2. Migration difficulty tiers (the answer to the question)

### Tier A — Nothing to migrate (re-created by the new stack) ✅ *zero risk*

| What | Why no migration |
|---|---|
| **Entire tender corpus** (~7.6M rows: notices, documents, extracted pages/text, coordinates, predictions) | The new pipeline re-ingests from source (DE_BUND + TED) with a 24-month backfill horizon. **Already done:** 44,865 tenders, 29,560 documents, 29,056 chunks live in Mongo. Re-fetching is cleaner than migrating derived/duplicated tables (`*_duplicate`, `etsd_duplicate`, `*_already_exists`, `backup_*`). |
| **CPV codes, NUTS regions** | Seeded from committed data (`db:seed:cpv`, `cpvcodes`=9,404 present). |
| **Geocoding cache** (53,920) | `geo_cache` rebuilds lazily on demand; cold-start miss cost only. |
| **AI outputs** — match scores, fit, verdicts, overviews, short summaries, analyses, reports | Regenerated by `ai:match` / `ai:overview` / report runs. Migrating stale AI output would just pin old model versions. Re-derive. |

**This tier is why the migration is small.** ~99.9% of the source rows are here.

### Tier B — Easy / mechanical ✅ *low risk, scriptable, idempotent*

| Entity | Source → Target | Notes |
|---|---|---|
| **Companies** | `companies` (268) → `companies` | Rich field map (§3.1). The target model even documents the mvp1 columns it replaces. **Friction:** target has `required` fields (`domain` unique, `website`, `businessDomain`, `region`) that some prod rows may leave null → a validation/cleanup pass is needed, not just a copy. |
| **User profiles → membership** | `profiles` (450) → `accountprofiles` + `companies.members[]` | `profiles.company_id` is the real tenant link (`memberships` is empty). Group profiles by company → build `members[]`; one `accountprofiles` per user. Role from `profiles.role`/`user_role`. |
| **Saved / disliked tenders** | `user_saved_tenders` (55) + `user_disliked_tenders` (250) → `tender_decisions` | One doc per (company, tender); saved → an active column, disliked → hidden status. Tender ids must resolve to re-ingested tenders (§7.3). |
| **Saved filters** | `saved_filter_profiles` (26) → saved-filters | JSON `filter_config` → the new filter shape; straightforward remap. |
| **CPV domain divisions** | `company_domain_cpv_divisions` (18) → onboarding seed | Tiny reference-ish table. |
| **Feedback** | `feedback` (54) → export or small collection | Optional; low value, trivial. |

### Tier C — Moderate ⚠️ *needs transforms, byte-copies, or reconciliation*

| Entity | Challenge |
|---|---|
| **Company documents + file bytes** | `documents` (57) + company logo/insurance/certification/reference arrays on the `companies` row → `companyfiles` + **S3**. Rows are just pointers; the **bytes live in ~7 Supabase Storage buckets** (`Company Documents Storage`, `Company Logos`, `documents`, `project-documents`, `doc-filler`, `chat-attachments`, `avatars`). Each object must be **downloaded and re-uploaded to our S3**, then re-embedded for Clara (`ai:embed:company`). See §7. |
| **Company knowledge base + embeddings** | `companies.knowledge_base` (JSON, free-form) → the **typed** `CompanyKnowledgeBase` sub-document (structured, ~10 nested groups). Shape differs → field-by-field coercion. `companies.embedding`/`combined_embedding` are **not migrated** — re-embedded by `ai:match` (dimension/model differ anyway: Gemini 1536-d). |
| **Kanban / workspace** | `work_space` (247) + `work_space_tender` (439) + `ws_tender_comment` (31) + `ws_clara_tender` (10) → `tender_decisions` (status) **plus** a comments target that only partially exists (proposal row 25). Must dedupe against saved/disliked/`company_tenders` so a tender isn't in two states. Reconciliation logic, not a copy. |
| **Chat history** | `chat_sessions` (1,277) + `chat_messages` (1,895) → `chat_threads` + `chat_messages`. **Display-only** is feasible; **resumable** is not — LangGraph state lives in `agent_checkpoints` keyed `clara:{tenantId}:{tenderId}` and cannot be reconstructed from old transcripts. Also `agent_type` includes `dora`/`nova` threads whose agents aren't ported. See §4.4. |
| **Employees / team** | `employees` (417) → no direct target (the Company model has `members[]` for *users*, not an HR roster). If the team-roster feature is kept, needs a new collection; otherwise drop. |

### Tier D — Hard / blocked ⛔ *cannot be done by a copy; needs a build or a decision*

| Blocker | Why it's hard | Path |
|---|---|---|
| **Auth password hashes** | Supabase stores **bcrypt** in `auth.users.encrypted_password`; Better Auth stores **scrypt**. Formats are not interchangeable, **and** `auth.users` is in the `auth` schema — **not exposed by PostgREST**, so even reading the hashes needs a direct Postgres connection or a `SECURITY DEFINER` RPC we don't have. | §5 — either (a) a direct DB dump + a Better Auth custom-verify shim that accepts bcrypt then rehashes, or (b) a password-reset campaign. Recommend (b) with (a) as an optional upgrade. |
| **Stripe billing** | `company_subscriptions` (182) references live Stripe objects (`stripe_customer_id`, `stripe_subscription_id`, price/schedule ids) + usage counters. **There is no billing schema in Mongo yet.** You cannot "recreate" a subscription — you must preserve the Stripe ids and re-link. | §6 — build the billing model first (proposal parity row 28), then migrate as an ID-preservation + reconciliation task, tested against Stripe test clocks. |
| **CAN winner/competitor intelligence** | 3,864 winner profiles + 15,912 matching rows + 584 insight rows. **No target schema.** It's a whole product surface (rows 29–30 in the proposal), currently 🗑️/❌. | Product decides keep-or-drop. If keep: design schema, then it becomes a Tier-B copy. |
| **Legacy ERP** | projects/tasks/inventory/warehouses/site-reports/etc. No target, out of product scope. | Propose **drop**; archive a Postgres dump for records. |
| **Notifications history** | 15,041 rows of transient delivery state (`notifications`, `company_tender_notification_sent`, `trial_email_log`). | **Don't migrate** — start fresh; it's operational, not user-authored. |

| Target | From | Notes |
|---|---|---|

### 3.3 Saved/disliked/workspace → `tender_decisions`

Target is **one doc per (company, tender)** with a kanban `status` (unique index `{companyId, tenderId}`). Sources overlap and must be merged with a priority order:

```
work_space_tender.tender_progress_status  (explicit column)  ── highest priority
company_tenders.workflow_status            (7,037 rows)
user_saved_tenders                         → saved/active column
user_disliked_tenders                      → hidden status         ── lowest, but overrides "unseen"
```

`decidedByUserId`/`assigneeUserId` from `added_by`/`assignTo`. **Every `tender_id` must resolve to a re-ingested tender** — matched by source notice id, not the old Postgres UUID (§7.3). Unresolvable ids (older than the backfill horizon) are logged and skipped.

## 4. Deep dives on the awkward pieces

### 4.4 Chat history — migrate as read-only, or start fresh

- **What transfers cleanly:** thread list + message transcripts for `agent_type='clara'` → `chat_threads` + `chat_messages` (display).
- **What does not:** the LangGraph **checkpoint state** (`agent_checkpoints`, keyed `clara:{tenantId}:{tenderId}`) cannot be reverse-engineered from a transcript. A migrated thread is **viewable but not continuable** — the first new message starts fresh agent state.
- **Orphans:** `dora`/`nova` sessions (those agents aren't ported) and `project_id`-linked ERP chats have no home.
- **Recommendation:** migrate Clara transcripts **read-only** into an "archived conversations" view **only if** product wants history; otherwise **start fresh** (1,277 sessions / 1,895 messages is low value against the complexity). Default: start fresh, export the old transcripts to cold storage.

## 5. The auth problem (Tier D, blocking user login)

**Facts established from the live DBs:**
- Target `account` docs are `providerId:"credential"` with a **scrypt** `password` (hex hash, sample prefix `129aa46…`). `lib/auth.ts` uses Better Auth's **default scrypt** — no custom hashing configured.
- Supabase stores **bcrypt** (`$2a$…`) in `auth.users.encrypted_password`.
- That column is **not reachable via PostgREST** (the `auth` schema isn't exposed). The admin API (`/auth/v1/admin/users`) returns profile metadata **but not the hash**. Of a 200-user sample, only **92 had a confirmed email** — a chunk of the 450 are likely dead/never-activated accounts.

**Options:**

| Option | What it takes | Pros / Cons |
|---|---|---|
| **A. Rehash-on-login shim** | Direct Postgres dump of `auth.users(id,email,encrypted_password)` (needs the DB password/pooler string — **not in the repo's `.env`**, must come from the Supabase dashboard), plus a Better Auth **custom password verify** that detects a `$2a$` hash, verifies with bcrypt, and transparently rehashes to scrypt on success | ✅ users keep passwords, seamless ❌ requires custom auth code + a direct DB credential we don't currently hold; dead accounts carried over |
| **B. Password-reset campaign** *(recommended)* | Migrate `user` rows with `emailVerified` preserved but **no** credential `account`; on first login send a branded "set your password" reset (Resend is already wired for auth mail) | ✅ no hash handling, no bcrypt dependency, naturally drops dead accounts ❌ every active user resets once (one email, one click) |
| **C. Hybrid** | B for everyone, offer A later if reset friction is real | Pragmatic default |

**Social logins (Google/Microsoft):** the provider sample returned no `identities` via the admin list endpoint, so the exact social/password split needs the direct `auth.identities` dump to quantify. Social users don't need a password at all — they need an OAuth `account` row (or simply re-consent on first login, which Better Auth handles). **Confirm the split during the Phase-2 rehearsal.**

**Recommendation: Option B**, with the reset campaign rehearsed on a staging copy, and A kept in reserve if product wants zero-reset UX.

## 6. The billing problem (Tier D, blocking paid customers)

- `company_subscriptions` (182) holds live **Stripe** linkage: `stripe_customer_id`, `stripe_subscription_id`, `stripe_price_id`, `stripe_schedule_id`, period bounds, cancel state, `pending_*` scheduled changes, and **per-agent monthly usage counters** (`clara_/dora_/nova_sessions_used_this_month`, `ai_analyses_used_this_month`, `doc_fills_used_this_month`). `subscription_plans` (8) + `subscription_addons` (6) are product config with dozens of feature flags.
- **Mongo has no billing schema** — `companies` carries only `trial`. So this is **build-then-migrate**, not migrate:
  1. Build the billing model in `bauai-nextjs` (proposal parity row 28) — subscription + plan/addon config + usage counters.
  2. Migrate as an **ID-preservation** task: copy Stripe ids verbatim so the existing customer/subscription objects keep working; re-link to the new `company` `_id`.
  3. Reconcile against Stripe as the source of truth (never trust the copied row for money state); test with **Stripe test clocks** in staging.
  4. Keep the MVP1 `stripe-webhook` **alive during the bake period** so no event is lost mid-cutover.
- **Do not** recreate subscriptions or usage counters from scratch — you'd double-bill or reset limits. This is the highest-risk migration item and gates paid-customer cutover.

19 buckets exist. Only user-authored, still-in-scope content moves:

| Bucket | Migrate? | Target |
|---|---|---|
| `Company Documents Storage`, `documents`, `project-documents` | ✅ | S3 `company-documents` prefix → `companyfiles` + re-embed |
| `Company Logos`, `avatars` | ✅ | S3; `companies.logoKey` / user avatar |
| `doc-filler`, `template-documents` | 🔶 | only if doc-filler ships in the ONLYOFFICE track |
| `chat-attachments` | 🔶 | only if chat history is migrated (§4.4) |
| `feedback-attachments` | 🔶 | with feedback, if kept |
| `tenders-raw`, `tender-zips`, `Tender Documents Storage` | ❌ | re-fetched by the new document pipeline |
| `Customer Documents`, `Lead Documents`, `Materials Storage`, `GAigentFiles`, `checklist-*`, `public-assets` | ❌ | legacy/ERP or re-derived |

**Mechanics:** for each in-scope object — download via the service-role Storage API → stream to our S3 (`@aws-sdk/lib-storage`) → write the `companyfiles` row with the new `s3Key` → enqueue `company_doc_embed`. Idempotent by content hash; re-runnable. Budget for a few GB and a rerun-until-clean pass on failures.

### 7.3 The ID-remapping problem (cross-cutting)

Old rows reference tenders by **Postgres UUID**; the re-ingested Mongo tenders have **new `_id`s** and are keyed by **source notice id** (version id → publication id). Every tenant row that points at a tender (`user_saved_tenders`, `work_space_tender`, `company_tenders`, `tender_analyses`, chat tender refs) must be **re-pointed by matching on the stable source notice id**, not the UUID. Build a `{old_tender_uuid → source_notice_id → new_mongo _id}` lookup first; rows whose tender predates the 24-month backfill horizon won't resolve — **log and skip** (they're stale saves anyway).

## 8. Sequenced runbook (fits Phase 2 of the proposal)

1. **Build the ID lookup** — export source notice ids for all live Mongo tenders; map old Postgres tender UUIDs → new `_id`.
2. **Companies** — clean + validate (§3.1), insert `companies` (no members yet). Emit a per-company validation report; fix required-field gaps.
3. **Users** — `user` rows with `emailVerified`; **auth path = Option B** (no credential rows); backfill `companies.members[]` + `accountprofiles`.
4. **Tender decisions** — merge saved/disliked/workspace/company_tenders → `tender_decisions` via the lookup; skip unresolved.
5. **Saved filters, CPV divisions, feedback** — small Tier-B copies.
6. **Storage bytes** — copy in-scope buckets → S3 → `companyfiles` → enqueue re-embed.
7. **Re-derive AI** — run `ai:match` / overviews so every migrated company has fresh scores (don't migrate stale AI output).
8. **Billing** *(after the billing model ships)* — ID-preserving subscription migration + Stripe reconciliation on test clocks.
9. **Chat** *(optional)* — read-only transcript import, or skip.
10. **Validate** — row-count parity per entity, checksum spot-checks, and a cross-tenant isolation probe (no company sees another's decisions/files). Every script **idempotent**, dry-run on staging first, with a documented rollback.

## 9. Decisions needed from product/leadership

1. **Auth:** password-reset campaign (Option B) vs. build the bcrypt rehash shim (Option A)? *(Recommend B.)*
2. **Billing:** confirm parity row 28 is built **before** cutover; who owns the Stripe reconciliation?
3. **Chat history:** migrate Clara transcripts read-only, or start fresh? *(Recommend start fresh.)*

6. **Historical tenders older than 24 months:** does any customer rely on saves that old? If yes, widen the backfill horizon or do a one-off import; if no, skip.

## Appendix — how these numbers were gathered (reproducible, read-only)

```bash
# Mongo inventory
docker exec bauai-ingestion-mongo-1 mongosh --quiet --eval \
  "db.getSiblingDB('bauai').getCollectionNames()"

# Supabase live table list + counts (service-role; Content-Range gives exact count)
curl -s "$URL/rest/v1/<table>?select=*" \
  -H "apikey: $KEY" -H "Authorization: Bearer $KEY" \
  -H "Prefer: count=exact" -H "Range: 0-0" -D - -o /dev/null | grep -i content-range

# Storage buckets
```
